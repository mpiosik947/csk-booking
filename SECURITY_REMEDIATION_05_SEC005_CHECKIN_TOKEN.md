# SECURITY REMEDIATION 05 — SEC-005 Check-in Token / PII Exposure

## Status

- **SEC-ID:** SEC-005
- **Original severity:** MEDIUM
- **Verdict:** **SEC-005 FULLY REMEDIATED**
- **Validated against:** local Supabase only
- **Production deployment:** not performed

## Before

`public.reservations.check_in_token` was a random, unique UUID stored in plaintext without an expiry column or lifecycle check. The public Server Component `/check-in/[token]` created a service-role client, selected a reservation directly by bearer token, bypassed RLS, and rendered the customer's name, e-mail, phone number, booking schedule, lane, reservation status and payment status.

The public GET did not mutate attendance, but possession of a leaked URL provided long-lived unauthenticated access to reservation PII. The token remained usable after cancellation, after check-in and after the reservation date. Application-generated links could also enter browser history; a referrer policy was not explicitly set.

## Threat model

| Scenario | Before | After |
|---|---|---|
| Old link opened long after the visit | CONFIRMED exposure | Denied after `end + 2h` |
| Token stored in browser history | LIKELY | URL remains a bearer capability, but it is time-bounded and public output contains no PII |
| Link copied to another person | CONFIRMED exposure | Copy reveals only neutral `ready` / `already_checked_in` / `unavailable` state |
| Token reused after check-in | CONFIRMED lookup reuse | Public response is controlled; staff lookup remains until window end; second `start` is idempotent |
| Excessive PII returned | CONFIRMED | Removed from the public contract |
| Token used after cancellation | CONFIRMED | Immediately returns `unavailable`; staff lookup returns no row |
| Token predicted or brute-forced | LOW | UUID remains generated by `gen_random_uuid()` and protected by a unique index |

Residual risk: the plaintext UUID still appears in the intended e-mail/QR URL and may be present in infrastructure access logs that record request paths. Application code does not log it. Hash-at-rest and URL redesign are intentionally outside this minimal remediation.

## Token lifecycle before

```text
gen_random_uuid()
→ plaintext reservations.check_in_token
→ confirmation e-mail / owner QR
→ public service-role SELECT by token
→ public PII response without an expiry check
→ authenticated admin/employee attendance mutation by reservation_id
→ public token continued to resolve indefinitely
```

## Token lifecycle after

```text
gen_random_uuid()
→ plaintext reservations.check_in_token
→ confirmation e-mail / owner QR
→ before start - 24h: unavailable
→ active window: anonymous RPC returns only { ok, code }
→ authenticated admin/employee resolves an allowlisted operational DTO
→ existing update_reservation_attendance performs the row-locked mutation
→ first start: started / changed=true
→ repeated start: already_started / changed=false / no second audit
→ public state after start: already_checked_in
→ cancellation or no_show: unavailable immediately
→ after end + 2h: unavailable
```

No parallel time calculation was introduced. Both readers use the shared database predicate over the existing `reservation_date`, `start_time` and `end_time`, interpreted in `Europe/Warsaw`.

## Expiry

- **Valid from:** local reservation start minus 24 hours.
- **Valid until:** local reservation end plus 2 hours, inclusive.
- **Time zone:** `Europe/Warsaw`.
- **Cancelled/canceled/cancelled_by_admin/cancelled_by_user:** invalid immediately because only `confirmed` and `completed` are eligible.
- **No-show:** invalid immediately.
- **Checked-in/present:** public status is `already_checked_in`; staff lookup remains available only until the same window ends.
- **Completed:** staff lookup and the neutral already-used state remain available only until the end of the window.

The implementation derives expiry from authoritative reservation timing, so no redundant `check_in_token_expires_at` column was added.

## Data minimization

### Public bearer DTO

The exact JSON shape is:

```json
{ "ok": true_or_false, "code": "ready|already_checked_in|unavailable" }
```

It never returns reservation/user identifiers, customer name, e-mail, phone, address, profile, date, time, lane, payment, attendance fields or any token. Invalid, cancelled, not-yet-active and expired tokens share the neutral `unavailable` result.

### Staff-only operational DTO

`get_check_in_reservation_v1(uuid)` is callable only by `authenticated` and additionally checks `auth.uid()` plus a `profiles.role` of exactly `admin` or `pracownik`. Its explicit allowlist supports the existing operator screen:

| Field group | Why required |
|---|---|
| `reservation_id`, `user_id` | controlled attendance/payment/cancellation RPC and existing reservation-scoped profile verification |
| customer name/contact | on-site identity and exceptional operational contact in the existing staff-only UI |
| reservation date/start/end | identify the scheduled visit |
| reservation/attendance/payment status and operational timestamps | calculate allowed staff actions and show current state |
| price | existing payment workflow |
| lane and parent display fields | unambiguous hierarchy-aware resource label |

It does not return `check_in_token`, reservation notes, addresses, a full profile or unrelated history. Instructor, ordinary user, anon and service role do not receive this DTO through the RPC.

## Implementation

The public page now uses the anon key and `get_public_check_in_status_v1(uuid)`. It no longer creates a service-role client or queries `reservations`. It is dynamic, fail-closed on malformed RPC data, sends `no-referrer` metadata and opts out of indexing.

The admin check-in token path now uses `get_check_in_reservation_v1(uuid)`, validates the UUID before the request, validates the response shape, and retains existing operational mutations. General staff list reads and the attendance writer were not changed.

No full token is written by application logging. The only public lookup error detail logged is the controlled provider error code.

## Migration

`20260902160000_harden_check_in_token_access.sql` adds only:

1. private shared lifecycle predicate `is_reservation_check_in_token_usable_v1(...)`;
2. anon-only neutral reader `get_public_check_in_status_v1(uuid)`;
3. authenticated, internally admin/employee-scoped reader `get_check_in_reservation_v1(uuid)`.

Both readers are `STABLE SECURITY DEFINER`, owned by `postgres`, use `search_path = pg_catalog, public, pg_temp`, qualify database objects, and expose explicit least-privilege ACL. The helper has no client `EXECUTE`. No table, token format, existing writer, RLS policy or business record is changed.

## Compatibility matrix

| Application / database | Result | Reason |
|---|---|---|
| OLD APP + OLD DB | SAFE functionally / INSECURE | legacy public service-role PII lookup remains |
| OLD APP + NEW DB | SAFE functionally / INSECURE | migration is additive; legacy table and service-role read remain until the application switch |
| NEW APP + OLD DB | UNSAFE | the two new RPCs do not exist, so public and staff token lookup fail closed |
| NEW APP + NEW DB | SAFE | lifecycle validation, minimal public DTO and staff-only lookup operate together |

## Deployment recommendation

Use **DB FIRST, THEN APP** as a coordinated two-step rollout:

1. deploy the additive migration;
2. verify both RPC signatures and ACL;
3. deploy the application immediately afterward;
4. smoke-test invalid, not-yet-active, valid, cancelled and already-used synthetic tokens;
5. verify that no public response or application log contains PII/token values.

If the application deployment fails after the migration, the old application remains functional because the migration does not revoke its service-role table access. If the application is deployed before the migration, token lookup fails closed but check-in is unavailable; therefore APP FIRST is not recommended.

## Regression risk

**MEDIUM**

The database change is additive and existing token UUIDs remain compatible, but the application and new RPCs must be rolled out in the stated order. Public users intentionally lose reservation-detail visibility; staff retains the operational flow through the scoped reader. No production write or deployment was performed during validation.

SEC-005 FULLY REMEDIATED
